# Project Knowledge Base Maintenance

This document defines the maintainer workflow for keeping the offline project
knowledge base (`.allthecodes/kb/`) trustworthy as the repository evolves. It
applies to every change that adds, edits, archives, or removes documentation
under `docs/` or `development/` — including the source-of-truth
`docs/WORK_STATUS.md`.

The KB is generated by `scripts/kb/build_project_kb.py` and is intentionally
**read-only at runtime**. Maintainers do not hand-edit the SQLite/JSONL/report
files. They update the markdown sources (or code) and let the KB rebuild from
those sources.

## Six-step update lifecycle

```text
Explore → Plan → Approve → Apply → Verify → Archive
```

Each step has a hard contract:

1. **Explore** — Read existing `docs/` and `development/` documents and the
   relevant Rust source. Use `python3 scripts/kb/build_project_kb.py --repo .
   query --q "<question>"` to learn which source documents already cover the
   subject and which source files are referenced by them. Do **not** propose
   changes yet.

2. **Plan** — Write or update a single plan under `development/docs/` (or
   `development/<area>/`) that records:
   - the source documents that need to change;
   - the source paths that need new frontmatter or status updates;
   - the generated KB outputs that will change as a side effect (`drift.json`,
     `kb-report.md`, `current-status.json`);
   - explicit acceptance criteria that name the verification commands below.

   Leave the plan's checkboxes `[ ]` while it is being drafted.

3. **Approve** — A human confirms the facts that will become current. The plan
   is only allowed to flip checkboxes to `[x]` after this approval. Approval is
   recorded verbally in the PR thread, in `development/<area>/<plan>.md`, or via
   a date-stamped entry under `## 决策` in the plan itself. No silent
   application is allowed for any fact that turns an archived row into a
   current one.

4. **Apply** — Run `python3 scripts/kb/build_project_kb.py --repo . build`
   after editing markdown. If a plan introduces a new architecture area, the
   plan task that establishes the area must also:
   - add a row under `docs/WORK_STATUS.md · ## 当前结论` summarizing what is
     now true (status = `current_status`);
   - add a row under `## 活跃文档入口` if the document becomes the
     source-of-truth entry for that topic.

5. **Verify** — Run the verification commands listed under
   [Review gates](#review-gates-and-the-check-command) below. The gate
   **refuses** to pass while any high-severity drift finding exists.

6. **Archive** — Move any now-historical detail out of active documents into
   `development/archive/**`. The active document keeps a one-paragraph summary
   plus a relative link to the archive copy. Do **not** rewrite the archive
   file's history — preserved sentences that reference legacy paths are fine
   once the file lives under `development/archive/**` (drift detection flags
   these as low-severity `legacy_path_reference` rather than high).

## Review gates and the `check` command

The build script exposes a dedicated `check` command that runs the full rebuild
plus a drift report and exits non-zero on high-severity findings:

```bash
python3 scripts/kb/build_project_kb.py --repo . check --fail-on high
```

`--fail-on` choices: `none`, `high` (default), `medium`.

The **high-severity** gate fails when any of the following drift categories
emits a finding:

| Category | Failure condition |
|----------|-------------------|
| `broken_markdown_link` | An active document links a relative Markdown target that does not resolve. |
| `missing_active_path` | An active document references a `crates/…`, `docs/…`, or `development/…` path that does not exist on disk (wildcards allowed). |
| `path_isolation_name_drift` | An active document mentions `.cc-rust`, `~/.cc-rust`, `.Codex`, or `~/.Codex` without an explicit historical / archive / legacy context word. |
| `archive_used_as_current_fact` | An active document cites an archived document as current guidance without naming it as historical / archived. |

The medium-severity gate additionally fails on:

| Category | Failure condition |
|----------|-------------------|
| `status_conflict` | An active plan marks itself `[x]` complete but `docs/WORK_STATUS.md` has not landed the work as `current_status`. |
| `duplicate_current_entry` | `docs/WORK_STATUS.md · ## 活跃文档入口` lists the same document twice. |

The low-severity `legacy_path_reference` finding is informational only: archive
documents that pre-date the allthecodes rename still cite `src/main.rs`,
`crates/cc-ipc-protocol`, etc. — historical fact, not a fix.

## PR and local output policy

`kb-report.md` and `drift.json` are generated locally under `.allthecodes/kb/`
by default. They are **not** committed (the directory is already gitignored by
allthecodes path isolation rules).

A PR may copy selected findings into `development/docs/` only when the findings
themselves need human review (for example, a `path_isolation_name_drift`
finding on a still-active `docs/README.md` section). Such PR-visible reports
must:

- live under `development/docs/<area>/kb-<date>.md` (not at the repository
  root, not under `docs/architecture/`);
- cite the underlying finding (`<path>:<line>` ranges);
- close out with the `check` command result so the next reader sees whether
  the gate ultimately passed.

Committed source for the KB itself lives in:

- `scripts/kb/build_project_kb.py`
- `scripts/kb/README.md`
- `development/docs/project-knowledge-base-organization-plan.md`
- `development/docs/project-knowledge-base-maintenance.md`

## Daily maintenance cadence

- **Before each documentation change**: run `query` with a topic phrasing to
  make sure the active document set already covers (or explicitly defers) that
  topic.
- **During the change**: keep the relevant plan's checkboxes `[ ]` until human
  approval is recorded; only then flip them in the same commit that adds the
  fact to `docs/WORK_STATUS.md`.
- **After the change**: run `check --fail-on high` locally before pushing. The
  gate is allowed to stay red only when a follow-up fix is tracked as a
  separate `path_isolation_name_drift` remediation plan.

## Why this workflow exists

The KB is the repository's "current truth" layer. Plans are speculative,
architecture docs are explanatory, and archives are historical — but
`docs/WORK_STATUS.md` is the only place the repository asserts *what is true
right now*. The six-step lifecycle protects that assertion. Skipping
`Approve`, in particular, is the most common way for archived facts to leak
back into current plans; the `archive_used_as_current_fact` high-severity
finding exists specifically to catch that slip.
